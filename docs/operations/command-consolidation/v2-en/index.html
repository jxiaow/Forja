Forja Command Consolidation v2

Goal: Consolidate ~107 scattered Qt/SDK/Remote/Sync commands into 10 intent-driven top-level commands, while keeping all existing functionality working through a compatibility layer.

Command specs (individual files): status · init · list · use · build · run · stop · clean · doctor · sync

1. End-User Command Set

forja status      — Current status and next-step suggestion
forja init        — First-time initialization (detect + save unambiguous config)
forja list        — Enumerate options (targets/servers/remote-repos)
forja use         — Select target, build config, execution endpoint
forja build       — Build current target
forja run         — Run current target
forja stop        — Stop currently running target
forja clean       — Clean build artifacts
forja doctor      — Deep diagnostics and recovery
forja sync        — Sync changed files to remote

forja remote, forja qt, forja sdk are not introduced as user commands. These remain as hidden compatibility entry points.

2. Core Concepts

2.1 ActiveTarget

All execution commands operate on the current target.

interface ActiveTarget {
    kind: 'qt' | 'sdk';
    project: string;       // workspace-relative path
    mode: 'debug' | 'release';
    arch: 'x86' | 'x64';
    runAt: 'local' | 'remote';
}

Rules:

  • kind must be explicit once selected; no guessing in mixed workspaces.
  • project prefers relative paths.
  • runAt is independent of kind: both Qt and SDK support local/remote.
  • When active target is missing, build/run/stop/clean return failure pointing to forja list + forja use.

2.2 Candidate

interface TargetCandidate {
    kind: 'qt' | 'sdk';
    project: string;
    label: string;
    current: boolean;
    configured: boolean;
    diagnostics: Diagnostic[];
}

2.3 Diagnostic

interface Diagnostic {
    code: string;                        // Stable machine code, format: <domain>.<condition>
    level: 'info' | 'warning' | 'error';
    message: string;                     // Human-readable text, follows locale
    hint?: string;                       // Human-readable hint, follows locale
    params?: Record<string, string>;     // Template variables for message/hint interpolation
}

code never changes with language. AI/scripts use code for decisions, not message text.

Diagnostic code naming: <domain>.<condition>, domains include workspace, target, toolchain, remote, sync, build, run, stop, clean, doctor.

2.4 JSON Envelope

interface ForjaJsonResult {
    ok: boolean;
    action: string;
    workspace?: string;
    activeTarget?: ActiveTarget;
    diagnostics?: Diagnostic[];
    nextActions?: string[];
}

Rules:

  • ok and action must always be present.
  • nextActions only outputs new commands, not legacy compatibility commands.
  • Text output may hint at compatibility command migration; JSON has no noisy copy.
  • Exit codes: success 0, failure 1, user cancel 0.

2.5 Readiness

type ReadinessState = 'ready' | 'configured' | 'blocked' | 'missing' | 'unknown' | 'not-selected';

interface Readiness {
    target?: ReadinessState;
    toolchain?: ReadinessState;
    sync?: ReadinessState;
    remote?: ReadinessState;
    runtime?: ReadinessState;
    transfer?: ReadinessState;
}

Semantics: ready = verified usable; configured = config exists but not deeply verified; not-selected = not selected; missing = required config missing; blocked = config exists but has blockers; unknown = cannot determine.

2.6 RuntimeState

interface RuntimeState {
    running: boolean;
    pid?: number;
    executablePath?: string;
    logFile?: string;
    runAt: 'local' | 'remote';
}

status --process to view, run --detach to start, stop to terminate. All three share the structure but have different responsibilities.

2.8 ServerSummary / ServerDetail

interface ServerSummary {
    id: string;
    name: string;
    host: string;
    port: number;
    username: string;
    authMode: 'key' | 'password';
    selected?: boolean;
}

interface ServerDetail extends ServerSummary {
    privateKeyPath?: string;
    strictHostKeyChecking?: boolean;
}

ServerDetail is used by forja list servers --detail <id>. No password output.

}

2.10 List vs Doctor Boundary

list answers "what exists", doctor answers "does it work". Toolchain detection (Qt/VS/jom/make scanning) is diagnostic in nature and belongs entirely to doctor.

QuestionCommandRationale
"What projects exist?"forja listFile scan, pure enumeration
"What servers exist?"forja list serversRead config, pure enumeration
"What remote repos exist?"forja list remote-reposRead config, pure enumeration
"Is Qt/VS/jom installed?"forja doctorSystem probing, diagnostic
"Can SSH connect?"forja doctorConnection verification, diagnostic
"Is sync config complete?"forja doctorConfig validation, diagnostic

2.11 Locale

Diagnostic messages and text output support multiple languages; code in JSON never changes.

Priority: --lang flag > FORJA_LANG env var > system locale > default en

forja status --json                  # default en
forja status --json --lang zh        # Chinese
FORJA_LANG=zh forja status --json    # Chinese

Affects:

  • Diagnostic.message, Diagnostic.hint — follows locale
  • Readiness text output — follows locale
  • CLI help, text mode output — follows locale

Does not affect:

  • Diagnostic.code — always English machine code
  • ReadinessState values — always ready/configured/blocked/missing/unknown/not-selected
  • nextActions command strings — always English commands

Readiness state text mapping:

6. Global Flags

FlagApplicable CommandsMeaning
--workspace <path>All commandsSpecify workspace. Defaults to current directory
--jsonAll commandsOutput structured JSON
--planinit, build, cleanPreview only, no externally impactful actions

Action & Flag Rules

forja <command> <action> [object] [--modifier-flags]
  • Actions use positional arguments: forja build qmake, forja doctor unlock <lock-id>, forja sync plan.
  • --flag only expresses modifiers: --json, --workspace, --force, --file.
  • Do not introduce --restore, --reset, --unlock, --clean-untracked as new public flags that are actually actions.
  • During migration, legacy flag forms remain compatible; new help, nextActions, and AI tool recommendations use positional actions only.

7. Text Output Specification

7.1 Language Strategy

CLI text output uses English. Current legacy command Chinese output is unified to English when migrating to new commands. Legacy command text output remains unchanged.

7.2 Unified Template

Forja <command> <result>

  <nextAction1>

Examples:

Next: forja doctor

8. Concurrency & Race Conditions

  • Remote execution: Existing lock mechanism (remote/core/lock.ts), prepare/release auto-managed.
  • Local execution: User-managed, no additional protection.
  • forja status: runtime field can indicate in-progress tasks (local reads runState, remote reads bridge ps).
  • runAt switching: If a build is in progress, use should warn but not block.

10. Implementation Stages

Stage 1: Foundation (no user-visible changes)

  • Create src/cli/unified/types.ts: ActiveTarget, Candidate, Result type definitions.
  • Create src/cli/unified/activeTarget.ts: Read/write active target metadata (stored at ~/.forja/projects/<hash>.json type=activeTarget).
  • Create src/cli/unified/candidates.ts: Qt/SDK target + server + remote-repo candidate aggregation.
  • Add tests for mixed workspace and single-target auto-selection.
  • Do not modify any existing commands.

Dependencies: None.

Verification: New modules compile; tests pass.

Stage 2: Config Commands

  • Create src/cli/unified/status.ts, init.ts, list.ts, use.ts.
  • Create src/cli/unified/index.ts: Top-level router for new commands.
  • Modify src/cli/index.ts: New commands matched first, fall through to legacy routing.
  • Update legacy Qt/SDK nextActions pointing to status/use/projects.
  • Add VSCode commands forja.status/forja.init/forja.list/forja.use, register + package.json.

Dependencies: Stage 1.

Can parallelize: Stage 3 (once activeTarget read/write is stable).

Verification:

  • forja status --json does not guess when no active target.
  • forja list --json lists Qt + SDK candidates.
  • forja use --target <path> --json saves active target.
  • forja init --json does not select in mixed workspace.

Stage 3: Execution Commands

  • Create build.ts, run.ts, stop.ts, clean.ts.
  • Implement build routing: default/fresh/qmake/rcc × qt/sdk × local/remote.
  • Implement run routing: default/detach/debug/custom.
  • Implement stop/clean routing.
  • Update status bar build/run/stop/clean invocations.

Dependencies: Stage 1 + Stage 2 activeTarget stability.

Can parallelize: Stage 2 (no shared logic beyond activeTarget).

Verification:

  • forja build --json routes by active target.
  • forja build qmake --json works for Qt, fails for SDK.
  • forja run --detach --json works for Qt, fails for SDK.
  • Remote selected target routes to existing remote prepared/bridge actions.

Stage 4: Diagnostics & Sync

  • Create doctor.ts, sync.ts.
  • Implement doctor aggregation: toolchain validation (Qt/VS/jom/make) + target + sync + remote checks.
  • Migrate qt env/sdk env entirely into doctor (toolchain scanning and validation all belong to doctor).
  • Absorb sync test-connection, remote test, remote doctor capabilities into doctor.
  • Preserve sync execution behavior, update nextActions to point to list/use.
  • Absorb cleanup capability into doctor fix.

Dependencies: Stage 2 (status pattern stable).

Verification:

  • forja doctor --json reports local target checks (local mode does not SSH).
  • forja doctor --remote --json reports remote checks.
  • forja sync plan --json preserves existing behavior.
  • sync missing config points to forja list servers + forja use --server.

Stage 5: Hide Compatibility Surface

  • Hide all legacy VSCode commands in package.json menus.commandPalette.
  • Retain all legacy command ID registrations.
  • Update CLI help: legacy qt/sdk/remote/sync config subcommands marked as compat.
  • Update AI skill documentation to use new commands.
  • Update docs/README-cli.md and docs/cli-interface-spec.md.

Dependencies: Stage 2-4 all complete.

Verification:

  • Command Palette search "Forja" only shows new command set + context commands.
  • forja --help shows new command set.
  • Legacy commands still executable.

Stage 6: Verification

  • npm run compile
  • npm test
  • npm run build:cli (CLI package includes new modules)
  • Do not run npm run package:all (unless explicitly packaging for release)

Dependencies: Stage 5.

13. Compatibility Strategy

After First Release

  • Legacy CLI subcommands continue to work.
  • Legacy VSCode command IDs continue to work.
  • Legacy commands hidden from main help and Command Palette.
  • Legacy command text output may include a brief migration hint; JSON does not add deprecation noise by default.

After Second Release

  • Retain legacy command execution (do not delete published VSCode command IDs).
  • Continue hiding legacy commands.

Invariants

  • Do not modify extension.ts activate function signature.
  • Do not delete published VSCode command IDs.
  • Do not modify published activationEvents in package.json.
